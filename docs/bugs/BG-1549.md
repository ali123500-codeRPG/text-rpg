# BG-1549

**What was wrong:** At story start the Weaver was told the player stands in the place `tavern`, so it built the tavern around them and put the headman's trigger on `player_seen_in_zone` `tavern.common`. Code started the player in the plan's first zone instead (the village green), so the opening and play began outside and that trigger might never fire. The start village was also cast without its roster (leader, service, seat of the Great), against SHEET-332.

**Root cause:** Both come from the Weaver's story-start view and prompt. `buildWeaverView` (`src/views/index.ts`) filled `player.standsIn` from `player.placeId`, which at story start is the bare place `CONFIG.STORY_START_PLACE` (`tavern`, `src/agents/game.ts`) while the player stands in no zone. Nothing in the plan could say where the player starts: `applyStagePlan` (`src/scenario/apply.ts`) read `arriveAt` only for a newcomer in a world with a past (`ctx.arrive`, BG-273) and otherwise moved a starting player into the first new zone (CS2), and only `target.wake` had a prompt line about that. The land's rosters were added only to the World builder's view (`withRosters` in `buildWorldView`, SHEET-340), and only the World builder's prompt said to cast them, so the Weaver, which builds the start settlement, never saw them.

**What was done:** PQ1 a: the start view's `player.standsIn` is null while the player stands in no zone, one prompt line tells the Weaver to set `arriveAt` to where the player starts (else they start in its first zone), and code and the plan check read `arriveAt` at story start as for a newcomer. The door start of BG-49 is unchanged. PQ2 a: the Weaver's start view runs `withRosters` on its land, and the World builder's roster rule is one shared string (`ROSTER_RULE` in `src/agents/prompts.ts`) used by both prompts. The Weaver's rule 7 ("Only uniques get goals") now also lets a seat of the Great from a roster have goals. The spec's two readings of where a story starts (scenario setup) now say the same thing.
